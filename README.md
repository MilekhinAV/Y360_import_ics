# Импорт ICS в Яндекс Календарь

`import_ics.py` читает файлы `.ics` из одной локальной папки и добавляет новые события в один выбранный календарь одного пользователя Яндекс 360. Существующие UID пропускаются. Доступ выполняется через временный пользовательский токен сервисного приложения и CalDAV.

## Установка

Python 3.10 или новее. Из папки проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

В Windows PowerShell вместо `source` используйте `.venv\Scripts\Activate.ps1`.

Единственная прямая зависимость — `icalendar` (её вспомогательные зависимости устанавливаются автоматически). Она нужна для разбора ICS, повторений, исключений и часовых поясов. HTTP, XML, CSV и работа с папками используют стандартную библиотеку Python.

## Создание приложения и получение токена

Ниже — пошаговая настройка одного OAuth-приложения: сначала с его помощью получаем токен владельца организации для регистрации, затем используем его ClientID и Client secret для импорта календарей.

### Шаг 1. Подготовьтесь

Перед началом убедитесь, что у вас есть:

- доступ к учётной записи **владельца организации (суперадминистратора)**;
- идентификатор организации Яндекс 360 (`ORG_ID`);
- настроенный почтовый домен и тариф, поддерживающий сервисные приложения;
- доступ к Интернету.

Все действия по получению административного OAuth-токена выполняйте под владельцем организации. Условия подключения приведены в [инструкции Яндекса](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications).

### Шаг 2. Откройте Яндекс OAuth

1. Перейдите на [oauth.yandex.ru](https://oauth.yandex.ru/).
2. Авторизуйтесь под владельцем организации.
3. Нажмите **Создать**.
4. Выберите **Для доступа к API или отладки**.
5. Нажмите **Перейти к созданию**.

### Шаг 3. Назовите приложение и выберите права

Укажите понятное название, например **ServiceApp_Calendar — импорт календарей**.

Добавьте права для работы с календарём:

```text
calendar:all
calendar:read_all
calendar:write_all
calendar:events.read
calendar:events.write
calendar:calendars.read
calendar:calendars.write
calendar:free_busy.read
calendar:resources.read
calendar:my_settings.read
calendar:my_settings.write
```

Это полный набор календарных прав из примера настройки, включая запись. Он шире потребностей импорта; скрипт не использует все эти возможности.

Также добавьте права для регистрации сервисного приложения:

```text
ya360_security:service_applications_read
ya360_security:service_applications_write
```

Календарные права разрешают работу с календарём. Два права `ya360_security:*` позволяют токену владельца управлять списком сервисных приложений организации.

### Шаг 4. Создайте приложение и сохраните реквизиты

1. Нажмите **Создать приложение**.
2. Откройте раздел **Общие сведения**.
3. Сохраните **ClientID** и **Client secret**.

ClientID понадобится для ссылки авторизации и регистрации приложения. Client secret понадобится в `.env` импортёра. Не публикуйте Client secret или токены в GitHub и переписке.

### Шаг 5. Сформируйте ссылку для получения токена

Скопируйте этот адрес:

```text
https://oauth.yandex.ru/authorize?response_type=token&client_id=YOUR_CLIENT_ID
```

Замените `YOUR_CLIENT_ID` полным значением **ClientID** из общих сведений приложения. Не добавляйте кавычки, пробелы или обратный слеш `\` перед идентификатором.

### Шаг 6. Разрешите доступ и получите токен

1. Откройте сформированную ссылку в браузере.
2. Убедитесь, что вошли под **владельцем нужной организации**.
3. Проверьте запрашиваемые права.
4. Подтвердите предоставление доступа.
5. Скопируйте выданный OAuth-токен и сохраните его в защищённом месте.

Этот токен далее называется `OWNER_TOKEN`. Он нужен для активации и регистрации приложения. Импортёр получает временные токены пользователей самостоятельно.

Если вы добавили права к уже существующему приложению, получите **новый токен**. Ранее выданный токен не приобретает новые разрешения автоматически.

### Шаг 7. Подготовьте терминал

Следующие команды предназначены для Bash или Zsh. Вместо `YOUR_ORG_ID` укажите числовой ID своей организации:

```bash
export ORG_ID="YOUR_ORG_ID"
```

Введите токен скрыто, чтобы не записывать его значение в историю команд.

**Zsh — стандартный терминал macOS:**

```zsh
read -r -s 'OWNER_TOKEN?Вставьте токен владельца: '
export OWNER_TOKEN
```

**Bash:**

```bash
read -r -s -p "Вставьте токен владельца: " OWNER_TOKEN
export OWNER_TOKEN
```

Вставьте токен и нажмите Enter. Символы при вводе не отображаются — это нормально. В командах ниже `${OWNER_TOKEN}` автоматически подставит это значение.

### Шаг 8. Активируйте сервисные приложения

Если функция в организации ещё не активирована, выполните:

```bash
curl --silent --show-error --fail-with-body \
  --request POST \
  "https://api360.yandex.net/security/v1/org/${ORG_ID}/service_applications/activate" \
  --header "Authorization: OAuth ${OWNER_TOKEN}"
```

Заголовок `Authorization` обязателен. Если `curl` не поддерживает `--fail-with-body`, обновите его или уберите этот параметр, проверяя ответ сервера вручную.

### Шаг 9. Зарегистрируйте приложение в организации

Сначала получите текущий список:

```bash
curl --silent --show-error --fail-with-body \
  "https://api360.yandex.net/security/v1/org/${ORG_ID}/service_applications" \
  --header "Authorization: OAuth ${OWNER_TOKEN}" \
  --output service_applications.current.json
```

Убедитесь, что запрос успешен. Создайте файл `service_applications.json` с полным желаемым списком. Если список пуст, содержимое может быть таким:

```json
{
  "applications": [
    {
      "id": "YOUR_CALENDAR_CLIENT_ID",
      "scopes": [
        "calendar:all",
        "calendar:read_all",
        "calendar:write_all",
        "calendar:events.read",
        "calendar:events.write",
        "calendar:calendars.read",
        "calendar:calendars.write",
        "calendar:free_busy.read",
        "calendar:resources.read",
        "calendar:my_settings.read",
        "calendar:my_settings.write"
      ]
    }
  ]
}
```

Замените `YOUR_CALENDAR_CLIENT_ID` значением ClientID приложения, созданного на шаге 4. В `scopes` при регистрации указываются календарные права; административные права `ya360_security:*` сюда добавлять не нужно.

**POST заменяет весь список приложений.** Если в организации уже подключены приложения, перенесите их объекты `id` и `scopes` из текущего списка в `applications` без изменений и добавьте календарное. Если этот ClientID уже присутствует, отредактируйте его запись вместо создания второй. Не отправляйте пример с единственным приложением поверх непустого списка.

Отправьте подготовленный файл:

```bash
curl --silent --show-error --fail-with-body \
  --request POST \
  "https://api360.yandex.net/security/v1/org/${ORG_ID}/service_applications" \
  --header "Authorization: OAuth ${OWNER_TOKEN}" \
  --header "Content-Type: application/json" \
  --data-binary @service_applications.json
```

Контракт замены списка: [документация метода](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Create).

### Шаг 10. Проверьте регистрацию

```bash
curl --silent --show-error --fail-with-body \
  "https://api360.yandex.net/security/v1/org/${ORG_ID}/service_applications" \
  --header "Authorization: OAuth ${OWNER_TOKEN}"
```

Убедитесь, что ответ содержит ваш ClientID, указанные календарные права и все ранее подключённые приложения. После настройки можно очистить переменную токена управления:

```bash
unset OWNER_TOKEN
```

Ошибка `No required scope` при регистрации указывает на недостающие права у токена владельца: проверьте `ya360_security:service_applications_write` и выпуск нового токена. Добавление `calendar:all` в JSON не выдаёт токену управления это разрешение.

Сервисное приложение предоставляет доступ. Папку проверяет локальный Python-процесс, который должен работать на компьютере с файлами. Временные пользовательские токены он получает самостоятельно.

## Настройки

Скопируйте `.env.example` в `.env` рядом с `import_ics.py`:

```dotenv
CLIENT_ID=your_calendar_service_app_id
CLIENT_SECRET=your_calendar_service_app_secret
USER_EMAIL=user@example.org
```

`USER_EMAIL` — адрес пользователя организации, в чей календарь записываются события. `CLIENT_ID` и `CLIENT_SECRET` принадлежат календарному сервисному приложению. `ORGID`, `ADMIN_TOKEN` и пароль пользователя для импорта не нужны: временный токен получается по email.

`.env` имеет формат `KEY=value`, кодировку UTF-8, допускает BOM, одинарные/двойные кавычки и комментарии отдельными строками с `#`. Подстановки `${...}`, многострочные значения и комментарии после значения не поддерживаются. Переменные окружения имеют приоритет над `.env`. Не публикуйте `.env` и не добавляйте его в Git.

## 1. Проверить файлы без записи

```bash
python import_ics.py --folder "/path/to/ics"
```

Команда не обращается к сети и не требует реквизитов. Она разбирает все `.ics` в указанной папке, считает файлы, компоненты VEVENT и уникальные UID. Подпапки не обходятся. Для одного UID несколько VEVENT могут описывать основное событие и исключения повторений.

Если файл некорректен, импорт всей папки останавливается до первой записи. В ошибке `file_N` означает номер файла в отсортированном по имени списке ICS этой папки. Содержимое событий в сообщении не выводится.

## 2. Получить список календарей пользователя

```bash
python import_ics.py --list-calendars
```

Будут выведены названия и CalDAV URL. Для первого импорта удобно заранее создать в веб-интерфейсе пользователя отдельный календарь, например «Импорт ICS». Скрипт сам календари не создаёт.

Скопируйте точный URL нужного календаря из вывода. Скрипт проверяет, что указанный календарь присутствует в списке выбранного пользователя. Право записи окончательно проверяется сервером при PUT.

## 3. Выполнить импорт

Замените URL в примере значением из предыдущего шага:

```bash
python import_ics.py \
  --folder "/path/to/ics" \
  --calendar-url "https://caldav.yandex.ru/calendars/user@example.org/calendar-id/" \
  --apply \
  --request-interval 5
```

Только `--apply` разрешает запись. Перед записью скрипт читает существующие UID из выбранного календаря. События с такими UID не изменяются. Новые события создаются условным PUT с `If-None-Match: *`, чтобы не перезаписать уже существующий ресурс.

После успешного PUT скрипт читает ресурс обратно и проверяет UID и набор исключений `RECURRENCE-ID`. Если GET по исходному адресу возвращает 404, скрипт ищет событие по точному UID через CalDAV REPORT: сервер может использовать другой адрес ресурса. Если событие ещё не видно, поиск повторяется с паузами 1 и 2 секунды; PUT повторно не отправляется. Эта проверка подтверждает наличие события и исключений, но не полное совпадение всех полей после обработки сервером.

## 4. Наблюдать за папкой

```bash
python import_ics.py \
  --folder "/path/to/ics" \
  --calendar-url "https://caldav.yandex.ru/calendars/user@example.org/calendar-id/" \
  --apply \
  --watch 120 \
  --request-interval 5
```

В многострочных командах Bash/Zsh обратный слеш `\` должен быть последним символом строки, без пробелов после него. Если забыть его перед строкой параметра, оболочка сообщит `command not found`.

После каждого завершённого прохода скрипт ждёт 120 секунд и повторяет проверку. Минимальный интервал — 60 секунд. Временный токен обновляется во время работы. Остановка — `Ctrl+C`.

Копируйте новый файл сначала с расширением `.part`, затем переименовывайте в `.ics` после завершения копирования. Иначе скрипт может прочитать неполный файл и остановиться. После неисправленной ошибки (в том числе после исчерпания повторов 429) режим наблюдения завершается; исправьте причину и запустите его снова.

Это импорт с пропуском существующих UID, а не двусторонняя синхронизация:

- Изменение уже импортированного UID в локальном файле не обновляет событие на сервере.
- Удаление файла не удаляет событие из календаря.
- Файлы после импорта остаются на месте.
- Если удалить событие из календаря, но оставить его в исходных ICS, следующий проход импортирует его снова.
- Не запускайте несколько импортёров для одного календаря одновременно. Коллизия или отказ условного PUT остановит импорт для проверки.

## Интервал запросов и HTTP 429

По умолчанию между началами любых HTTP-запросов выдерживается минимум 2 секунды, включая OAuth, PROPFIND, REPORT, PUT и GET. Это общий интервал одного процесса; параллельные запуски не координируются. Длительность самого запроса засчитывается в интервал.

Для начала используйте интервал 5 секунд, как в командах выше. При необходимости его можно увеличить:

```bash
--request-interval 5
```

Допустимо любое конечное число не меньше нуля; `0` отключает обычную паузу. `--watch` задаёт отдельную паузу между проходами папки.

При 429 учитывается `Retry-After` в секундах или формате HTTP-даты. Если заголовок отсутствует или некорректен, паузы составляют 30, 60 и 120 секунд. Ожидание сервера не сокращается до обычного интервала. Скрипт сообщает длительность ожидания и номер повтора без вывода секретов. Максимум — три повтора каждого запроса после 429; после исчерпания лимита импорт останавливается. Перед повторной записью выполняется поиск UID. Найденное событие проходит обычную проверку UID/исключений. Если поиск завершился ошибкой, PUT не повторяется.

Пауза снижает частоту запросов, но не гарантирует отсутствие 429: ограничения могут быть общими с другими клиентами.

## Что переносится

Сохраняются UID, название, описание, место, время, события на весь день, правила повторения, EXDATE/RDATE и исключения RECURRENCE-ID. Компоненты VTIMEZONE включаются в создаваемые объекты. Окончательная поддержка свойств зависит от сервера Яндекс Календаря.

**Создаются личные копии событий:** ORGANIZER, ATTENDEE и VALARM удаляются из отправляемых данных; METHOD и запрос автоматического создания Телемоста не передаются. Поэтому импорт не предназначен для рассылки приглашений, переноса ответов участников или напоминаний. Настройки уведомлений самого целевого календаря скрипт не меняет. Уже существующие ссылки на встречи в описаниях сохраняются.

## Требования к ICS и ограничения

- Один файл может содержать много событий. Серии с одинаковым UID собираются в один ресурс, в том числе из нескольких файлов.
- Повторяющиеся одинаковые компоненты в исходных файлах объединяются. Разные версии одного UID + RECURRENCE-ID вызывают ошибку, чтобы не выбирать версию молча.
- Обязательны UID, DTSTART и DTSTAMP. Исключение без основного события отвергается.
- Поддерживаются VEVENT и VTIMEZONE. Задачи VTODO, журналы VJOURNAL и другие компоненты требуют отдельного импортёра.
- ICS — UTF-8, допустим BOM. Максимальный размер одного файла и ответа сервера — 64 MiB.
- Различные определения одного TZID в разных файлах считаются конфликтом.
- Время без TZID и без `Z` остаётся «плавающим»: его трактовку определяет календарный клиент/сервер. Для предсказуемого времени используйте экспорт с часовыми поясами.
- Очень большие календари могут не пройти REPORT по всем UID из-за ограничений сервера; в таком случае запись не начинается.

## Отчёт и ошибки

Каждый проход импорта создаёт CSV в текущей папке терминала:

```text
import_report_YYYYMMDD_HHMMSS_microseconds.csv
```

Время в имени — UTC. Кодировка UTF-8 с BOM, разделитель `;`.

| Поле | Значение |
| --- | --- |
| `uid_sha256` | SHA-256 исходного UID; тот же идентификатор используется в имени ресурса CalDAV |
| `status` | `created`, `skipped` или `needs_check` |
| `error` | Безопасный этап/код ошибки |

`created` означает, что создание и проверка UID/исключений прошли. `skipped` — UID уже был в выбранном календаре. `needs_check` — возникла ошибка записи или проверки; событие могло успеть создаться. После такой строки импорт останавливается, оставшиеся события не обрабатываются. Проверьте последний ресурс перед повторным запуском. Если он создан правильно, следующий запуск найдёт его UID и пропустит.

При HTTP 429 выполняется до трёх повторов после ожидания. Перед повтором PUT скрипт ищет UID: если событие уже существует, проверяет найденное событие без повторной записи. Сетевые ошибки PUT автоматически не повторяются. Также повторяется поиск по UID после GET 404, как описано выше. Ошибка сети после PUT не доказывает, что сервер не применил запись. Если GET-проверка обнаружила потерю исключений, повторный запуск не исправит событие автоматически: существующий UID будет пропущен.

| Ошибка | Что проверить |
| --- | --- |
| `POST:http_400:invalid_client` | ClientID и секрет одного календарного сервисного приложения |
| `POST:http_400:invalid_request` | Подключение приложения к организации, параметры обмена токена и целевой аккаунт |
| `PROPFIND:http_403` / `REPORT:http_403` | Доступ к календарю, права приложения, состояние пользователя |
| `PUT:http_429` | Лимит сохраняется после повторов; увеличьте `--request-interval`, исключите параллельные запуски и повторите позже |
| `PUT:http_403` | Право записи в выбранный календарь |
| `PUT:http_412` | Ресурс уже существует; проверьте его, не перезаписывайте вслепую |
| `PUT:network_error` | Неопределённый исход записи: проверьте календарь перед повтором |
| `verification_uid_not_found` | После создания событие не найдено ни по исходному URL, ни по UID; проверьте календарь |
| `verification_failed` | Сервер вернул другой UID или набор исключений |
| `incomplete_uid_report` | Не удалось получить полный список UID; запись не начинается |
| `calendar_not_found` | Используйте точный URL из `--list-calendars` для того же USER_EMAIL |

Токены, Client secret, сырые HTTP-ответы и содержимое событий не выводятся. Из ошибки OAuth выводятся только известные коды. Названия календарей и их URL выводятся только при явном запросе `--list-calendars`.

Коды выхода: `0` — проверка/импорт завершены успешно, `1` — ошибка или требуется проверка результата записи, `2` — неверные аргументы запуска, `130` — остановка через Ctrl+C.

## Проверка разработки

```bash
python -m unittest -v
```

Тесты выполняются на искусственных ICS и подставных ответах HTTP. Живая интеграция с календарём конкретной организации требует отдельного пробного импорта.
